# План доработки: Welcome-функционал

## 1. Цель

Добавить в Discord Translation Bot настраиваемое приветствие новых участников сервера.

После входа нового участника бот должен отправлять в выбранный администратором welcome-канал сообщение, которое включает:

- упоминание нового участника;
- настраиваемый текст;
- небольшое изображение, загруженное администратором;
- кнопку перехода в канал выбора языка `#choose-language`;
- при необходимости дополнительные настраиваемые кнопки;
- ссылки или Discord-упоминания других каналов в тексте.

Документ является предварительным бизнес-анализом и планом. Спорные решения перечислены как открытые вопросы. Реализация кода в этот этап не входит.

## 2. Текущее состояние проекта

- Бот работает на нескольких Discord-серверах, поэтому конфигурация должна храниться отдельно для каждого `guild_id`.
- Настройки уже сохраняются в SQLite локально и PostgreSQL на Railway через SQLAlchemy.
- Административные slash-команды защищены разрешением `Manage Server` (`manage_guild`).
- `/setup_server` создаёт или переиспользует `#choose-language`, а `LanguageSetupMessage` хранит идентификатор опубликованного меню выбора языка.
- Постоянный dropdown выбора языка регистрируется при запуске бота.
- Обработчика входа участника (`on_member_join`) и welcome-моделей сейчас нет.
- Включён стандартный набор Discord intents, но member intent явно не включён. Для надёжной обработки входа участников потребуется включить соответствующий intent в коде и Discord Developer Portal.
- Railway запускает единственный процесс командой `python -m app.bot`.

## 3. Участники и роли

### Администратор сервера

- включает, изменяет, проверяет и отключает welcome-функционал;
- выбирает welcome-канал и канал назначения основной кнопки;
- задаёт текст, изображение и кнопки;
- запускает тестовый preview без необходимости приглашать нового пользователя.

### Новый участник

- получает публичное приветствие с упоминанием;
- переходит по кнопке в `#choose-language` или по другим настроенным ссылкам.

### Бот

- валидирует и сохраняет конфигурацию отдельно для каждого сервера;
- реагирует на событие входа участника;
- безопасно формирует и отправляет сообщение;
- логирует результат без сохранения чувствительного содержимого в операционных логах.

## 4. Предлагаемый MVP

### Входит в MVP

1. Одна welcome-конфигурация на сервер.
2. Включение и отключение функции.
3. Выбор одного welcome-канала.
4. Настраиваемый текст приветствия.
5. Подстановка упоминания нового участника.
6. Одно загруженное изображение.
7. Обязательная основная кнопка перехода в выбранный канал, по умолчанию — в настроенный `#choose-language`.
8. Возможность использовать в тексте Discord channel mentions вида `<#channel_id>`.
9. Preview/test-команда для администратора.
10. Проверка конфигурации и прав бота.
11. Безопасное обновление существующей конфигурации и полное отключение без удаления других настроек бота.

### Следующий этап после MVP

- несколько дополнительных кнопок с настраиваемыми названиями и назначениями;
- шаблонные переменные помимо пользователя, например название сервера;
- локализованные welcome-сообщения;
- отдельные приветствия по ролям или источнику приглашения;
- журнал статистики входов и кликов.

### Не входит в текущую доработку

- личные welcome-сообщения в DM;
- автоматическая модерация новых участников;
- конструктор изображений, баннеров или карточек;
- аналитика кликов по link-кнопкам;
- перевод welcome-текста через AI;
- изменение существующей логики переводов и языковых ролей.

## 5. Пользовательские сценарии

### UC-01 — Первичная настройка

1. Администратор запускает команду настройки welcome-функции.
2. Выбирает канал публикации.
3. Указывает текст сообщения.
4. Загружает изображение.
5. Выбирает канал для основной кнопки и задаёт её название либо принимает значение по умолчанию.
6. Бот валидирует разрешения, изображение и обязательные поля.
7. Бот сохраняет конфигурацию и показывает preview.
8. Администратор подтверждает включение функции либо корректирует настройки.

### UC-02 — Вход нового участника

1. Discord передаёт боту событие входа участника.
2. Бот загружает конфигурацию этого сервера.
3. Если функция включена, бот проверяет существование welcome-канала и канала основной кнопки.
4. Бот формирует текст, разрешая упоминание только вошедшего участника.
5. Бот отправляет сообщение, изображение и кнопки.
6. Результат отправки фиксируется в структурированном логе.

### UC-03 — Проверка администратором

1. Администратор запускает preview/test-команду.
2. Бот формирует сообщение так, как если бы администратор был новым участником.
3. Preview публикуется только после явного выбора режима: приватный preview или тестовая отправка в welcome-канал.
4. Настройка не должна создавать фиктивную запись о входе пользователя.

### UC-04 — Изменение или отключение

1. Администратор заменяет отдельное поле либо всю конфигурацию.
2. Новые параметры применяются только к будущим сообщениям.
3. Уже опубликованные welcome-сообщения не редактируются.
4. При отключении конфигурация может сохраняться для повторного включения; удаление должно быть отдельным явным действием.

## 6. Функциональные требования

### FR-001 — Конфигурация на уровне сервера

Система должна хранить не более одной активной welcome-конфигурации на `guild_id`. Настройки разных серверов не должны влиять друг на друга.

### FR-002 — Welcome-канал

Администратор должен выбрать текстовый канал, в который бот будет публиковать приветствия. Перед сохранением или включением бот должен проверить наличие как минимум прав `View Channel`, `Send Messages`, `Embed Links` и `Attach Files`.

### FR-003 — Текст и упоминание пользователя

Администратор должен задавать текст приветствия. В шаблоне следует поддержать обязательную переменную `{user}`, которая при отправке заменяется на упоминание вошедшего участника.

Если `{user}` отсутствует, предлагаемый безопасный default — автоматически добавить упоминание перед текстом. Это предположение требует подтверждения.

### FR-004 — Ссылки на каналы в тексте

Бот должен сохранять Discord channel mentions без изменения и отправлять их в формате `<#channel_id>`, чтобы Discord отображал переход в соответствующий канал.

Настроенные упоминания `@everyone`, `@here`, произвольных пользователей и ролей не должны создавать массовые или посторонние уведомления. Разрешённое фактическое упоминание — только новый участник.

### FR-005 — Изображение

Администратор должен загрузить одно поддерживаемое растровое изображение. Бот должен проверить MIME-тип и лимит размера до сохранения и сообщить понятную ошибку при отказе.

Рекомендуемое хранение для Railway: бинарные данные и метаданные изображения в БД. Локальная файловая система Railway не должна использоваться как постоянное хранилище. Конкретный максимальный размер необходимо утвердить до реализации.

### FR-006 — Основная кнопка

Welcome-сообщение должно содержать link-кнопку, ведущую в выбранный канал Discord. URL формируется из `guild_id` и `channel_id`; администратору не требуется вручную вводить URL.

По умолчанию кнопка должна вести в канал, где размещено отслеживаемое сообщение выбора языка. Если такой канал не настроен, включение welcome-функции должно быть заблокировано либо администратор должен явно выбрать другой канал.

### FR-007 — Дополнительные кнопки

Архитектура данных должна допускать несколько упорядоченных кнопок. Каждая кнопка содержит название, тип назначения и назначение: канал текущего сервера или разрешённый HTTPS URL.

Количество и длины полей должны валидироваться по актуальным ограничениям Discord. Для MVP UI можно реализовать только основную кнопку, не блокируя последующее добавление остальных.

### FR-008 — Управление состоянием

Администратор должен иметь возможность:

- посмотреть текущую конфигурацию;
- создать или обновить её;
- заменить или удалить изображение;
- включить или отключить отправку;
- удалить конфигурацию отдельным явным действием;
- выполнить preview/test.

### FR-009 — Обработка входа

При событии входа человека или бота система должна применить утверждённое правило. Предлагаемый default — приветствовать людей и не публиковать сообщения для bot accounts.

Повторно доставленное событие не должно приводить к неконтролируемому потоку сообщений. Необходимость строгой дедупликации по паре `guild_id + member_id` требует решения с учётом повторных входов одного пользователя.

### FR-010 — Ошибки конфигурации

Если welcome-канал удалён, назначение кнопки недоступно или у бота пропали права, бот не должен падать. Он должен записать структурированное предупреждение. `/setup_check` либо отдельная welcome check-команда должна показать администратору проблему.

## 7. Данные

### WelcomeSetting

Предлагаемые поля:

- `id`;
- `guild_id` — уникальный идентификатор сервера;
- `is_enabled`;
- `welcome_channel_id`;
- `message_template`;
- `primary_button_label`;
- `primary_button_channel_id`;
- `image_bytes` или ссылка на отдельную запись изображения;
- `image_content_type`;
- `image_filename`;
- `created_at`;
- `updated_at`.

### WelcomeButton

Для расширяемых дополнительных кнопок:

- `id`;
- `welcome_setting_id`;
- `position`;
- `label`;
- `destination_type` (`channel` или `url`);
- `destination_value`;
- опциональный emoji;
- `created_at`;
- `updated_at`.

Отдельная таблица кнопок предпочтительнее JSON-поля: она упрощает валидацию, порядок, изменение одной кнопки и переносимость между SQLite и PostgreSQL.

## 8. Предлагаемый интерфейс администратора

Предварительный набор slash-команд:

- `/welcome_setup` — создать или обновить основные настройки;
- `/welcome_preview` — показать результат без изменения настроек;
- `/welcome_status` — показать состояние и найденные проблемы;
- `/welcome_enable`;
- `/welcome_disable`;
- `/welcome_image_set` и `/welcome_image_remove`;
- `/welcome_button_add`, `/welcome_button_remove`, `/welcome_button_list` — этап дополнительных кнопок;
- `/welcome_delete` — полностью удалить конфигурацию с явным подтверждением.

Для длинного текста удобнее Discord modal, открываемая командой настройки. Точный UX необходимо проверить на прототипе с учётом ограничений slash-команд, modal и вложений: загрузка attachment и ввод текста могут потребовать двух последовательных команд.

Все команды изменения должны требовать `Manage Server`, как текущие административные команды проекта.

## 9. Нефункциональные и эксплуатационные требования

- Ошибка welcome-функции не должна останавливать обработку переводов и запуск бота.
- Текст сообщения и бинарное изображение не должны попадать в обычные операционные логи.
- В логах допустимы `guild_id`, `channel_id`, `member_id`, статус операции и тип ошибки.
- Отправка должна использовать явную настройку `AllowedMentions`, разрешающую только упоминание текущего нового участника.
- Вводимые внешние ссылки должны приниматься только по утверждённым схемам; предлагается разрешить только HTTPS.
- Конфигурация должна работать одинаково с SQLite и PostgreSQL.
- Новые таблицы должны создаваться безопасно для уже развёрнутой БД без потери существующих данных.
- При нескольких экземплярах бота возможна двойная обработка join-события; текущая Railway-конфигурация предполагает один процесс, но это ограничение нужно задокументировать или добавить дедупликацию.

## 10. Критерии приёмки MVP

1. При настроенной и включённой функции вход нового обычного участника создаёт ровно одно welcome-сообщение в выбранном канале при штатной однопроцессной работе.
2. Сообщение содержит кликабельное упоминание вошедшего пользователя, настроенный текст, изображение и кнопку.
3. Основная кнопка открывает выбранный канал текущего сервера.
4. Указанные администратором channel mentions отображаются как переходы на каналы.
5. `@everyone`, `@here`, роли и посторонние пользователи из шаблона не получают уведомлений.
6. Настройки одного сервера не используются на другом сервере.
7. Неавторизованный пользователь не может просматривать чувствительные детали или менять welcome-конфигурацию.
8. Неподдерживаемое либо слишком большое изображение отклоняется без изменения действующей конфигурации.
9. При отсутствии нужных прав preview/status сообщает, каких разрешений не хватает.
10. При удалённом welcome-канале или канале кнопки обработчик не падает и оставляет диагностический лог.
11. Отключённая функция не публикует сообщения, но её настройки доступны для последующего включения.
12. Все существующие тесты переводов и настройки языков продолжают проходить.

## 13. Последовательность и контрольные точки

### M1 — Требования утверждены

- закрыты критические вопросы;
- утверждён MVP;
- согласован способ хранения картинки и UX настройки.

### M2 — Техническая основа готова

- добавлены модели и member intent;
- существующая БД обновляется безопасно;
- сервис формирует корректный preview.

### M3 — Feature complete

- работает настройка и обработка join;
- добавлены permissions и диагностика;
- реализованы тесты ошибок и безопасности упоминаний.

### M4 — Приёмка и релиз

- пройден end-to-end тест в Discord;
- документация обновлена;
- Railway-деплой проверен;
- известен быстрый rollback: отключение welcome feature flag/конфигурации без отката переводов.

| R-01 | Server Members Intent не включён в Developer Portal | Join-события не приходят | Добавить проверку запуска и явный шаг в admin docs |

| R-08 | Несколько экземпляров бота обрабатывают один join | Дубликаты приветствий | Один worker в MVP либо таблица/idempotency window в расширенной версии |
| R-09 | Дополнительные кнопки превышают ограничения Discord | Ошибка отправки | Валидировать количество и длины по актуальной версии Discord API |

## 15. Принятые решения

1. Welcome-сообщение использует сочетание обычного текста и embed с изображением.
2. Бот приветствует только людей; bot accounts пропускаются.
3. В MVP достаточно одной кнопки.
4. Загруженное изображение хранится в существующей SQLite/PostgreSQL БД. Внешнее хранилище и отдельная подписка не требуются.
5. Кнопка опциональна. Если администратор включает кнопку, но не выбирает языковой канал, бот выводит ошибку `Выберите языковой канал`.
6. Приоритет UX — визуально простая и понятная настройка с минимальным количеством команд и preview результата.

3. Нужна ли дедупликация при горизонтальном масштабировании на несколько экземпляров бота?

Функция **готова к реализации MVP**. Критические продуктовые решения утверждены. Открытые вопросы раздела 16 относятся к последующим расширениям и не блокируют разработку текущей версии.

# Этап 2: баннер, персонализация и редактирование

## 18. Статус и цель этапа

Базовый welcome-функционал реализован и проверен в production. Следующая доработка должна улучшить внешний вид сообщения и убрать необходимость повторно проходить `/welcome setup` при изменении текста или баннера.

Подтверждённые изменения:

1. Загруженное изображение отображается как широкий невысокий баннер по ширине embed.
2. Администратор может редактировать существующее welcome-сообщение без повторной первичной настройки.
3. В шаблоне доступна переменная `{server_name}`.
4. На баннер динамически накладываются круглая аватарка нового участника, его отображаемое Discord-имя и название сервера.
5. На этом этапе изменяется существующий welcome-функционал; логика переводов, языковых ролей и кнопки не расширяется.

## 19. Результат для пользователя

После входа нового участника welcome-сообщение состоит из:

- обычного текста с безопасным упоминанием пользователя и поддержкой `{server_name}`;
- широкого баннера в embed;
- круглой аватарки вошедшего участника слева по вертикальному центру баннера;
- крупного Discord-ника участника справа от аватарки;
- названия сервера меньшим шрифтом под ником;
- ранее настроенной опциональной кнопки языкового канала.

Администратор может отдельно:

- изменить текст и название кнопки;
- заменить баннер;
- посмотреть preview;
- сохранить остальные настройки без повторного выбора каналов и повторной загрузки картинки.

## 20. Анализ визуального решения

### Ограничение Discord

Discord embed умеет показать картинку, но не умеет самостоятельно накладывать аватар и текст поверх неё. Поэтому на событии входа бот должен создать итоговое растровое изображение:

```text
сохранённый баннер + аватар пользователя + display name пользователя + server name = итоговый PNG
```

Итоговый PNG прикрепляется к сообщению и показывается через `embed.set_image`. Отдельный внешний сервис не требуется: композиция выполняется в памяти процесса Railway.

### Рекомендуемый формат баннера

Discord-клиент адаптивный, поэтому гарантировать одинаковое физическое количество пикселей на всех экранах невозможно. Практический способ получить баннер по ширине сообщения — использовать широкое соотношение сторон и передавать его как основное embed-изображение.

Предлагаемый default:

- итоговый холст — широкое соотношение `4:1`;
- исходная картинка масштабируется с сохранением пропорций;
- лишние края обрезаются по центру, без растяжения;
- круглый аватар размещается слева по вертикальному центру с внутренними отступами;
- справа от аватара располагается текстовый блок, также выровненный по вертикальному центру;
- первая строка текстового блока содержит крупный `display_name` участника;
- вторая строка под ником содержит актуальное название сервера меньшим шрифтом;
- под аватаром и текстовым блоком применяется лёгкое затемнение или тень для читаемости на светлом и тёмном фоне;
- результат сохраняется в PNG независимо от исходного формата.

Точное рабочее разрешение и размеры элементов должны быть выбраны при визуальном прототипировании. Они не являются бизнес-правилом и могут корректироваться без изменения данных.

## 21. Функциональные требования этапа 2

### FR2-001 — Нормализация баннера

При сохранении или формировании welcome-изображения система должна преобразовать загруженную картинку в широкий баннер с утверждённым соотношением сторон.

Правила:

- изображение не растягивается с нарушением пропорций;
- изображение масштабируется до заполнения холста;
- лишняя область обрезается по центру;
- слишком маленькое или повреждённое изображение отклоняется с понятным сообщением;
- текущий лимит загружаемого файла сохраняется, если во время прототипирования не будет подтверждена необходимость его изменить.

### FR2-002 — Динамическая композиция

При входе нового человека система должна получить его актуальный Discord avatar, привести его к круглой форме и наложить на сохранённый баннер.

Справа от аватара должен отображаться `member.display_name`: серверный nickname, а при его отсутствии — глобальное отображаемое имя/username, предоставленное Discord-моделью участника. Ник отображается крупным шрифтом.

Непосредственно под ником должно отображаться актуальное `member.guild.name` меньшим шрифтом. Ник и название сервера образуют единый текстовый блок, выровненный по вертикальному центру относительно баннера.

Составной файл создаётся в памяти и не сохраняется в БД для каждого участника. В БД продолжает храниться только исходный баннер конфигурации.

### FR2-003 — Обработка длинного или сложного ника

Ник и название сервера не должны выходить за границы баннера, перекрывать аватар или друг друга.

Предлагаемое правило:

- сначала уменьшать размер шрифта до установленного минимального значения;
- если строка всё ещё не помещается, обрезать её с многоточием;
- применять эти правила независимо к нику и названию сервера, сохраняя визуальную иерархию: ник крупнее названия сервера;
- не изменять реальное имя участника в обычном тексте сообщения;
- неподдерживаемые шрифтом символы не должны приводить к падению обработчика.

### FR2-004 — Fallback аватара

Если у пользователя нет собственного avatar, используется стандартный Discord avatar. Если загрузить avatar не удалось, welcome-сообщение всё равно должно быть отправлено с предсказуемым fallback: баннер без аватара либо локальная нейтральная заглушка.

Рекомендуемый вариант — включённая в проект локальная заглушка, чтобы результат не зависел от сети после неудачной загрузки.

### FR2-005 — Переменная `{server_name}`

Перед отправкой и preview система должна заменять `{server_name}` на текущее имя Discord-сервера.

Пример шаблона:

```text
Добро пожаловать на {server_name}, {user}!
```

Результат:

```text
Добро пожаловать на My Community, @NewMember!
```

Значение берётся из `member.guild.name` в момент отправки, поэтому переименование сервера не требует обновления welcome-конфигурации. `{server_name}` является обычным текстом и не создаёт упоминаний.

### FR2-006 — Редактирование текста

Команда `/welcome edit` должна открывать короткую форму с уже заполненными текущими значениями:

- текст welcome-сообщения;
- название кнопки, если кнопка включена.

После сохранения меняются только эти поля. Welcome-канал, языковой канал, состояние функции и баннер должны остаться без изменений.

Если welcome ещё не настроен, команда сообщает, что сначала необходимо выполнить `/welcome setup`.

### FR2-007 — Замена баннера

Отдельная команда `/welcome banner` должна принимать новое изображение, валидировать его и заменять только сохранённый баннер.

После успешной замены бот показывает preview с администратором в роли тестового участника. При ошибке действующий баннер не изменяется.

### FR2-008 — Preview после редактирования

`/welcome preview`, результат `/welcome edit` и результат `/welcome banner` должны использовать тот же pipeline композиции, что и реальное join-событие.

Это означает, что администратор видит:

- фактическое кадрирование баннера;
- свою аватарку и display name;
- название сервера под ником на баннере;
- результат подстановки `{server_name}` в обычном тексте;
- реальный текст и кнопку.

### FR2-009 — Обратная совместимость

Существующие welcome-конфигурации должны продолжить работать после деплоя без повторного `/welcome setup`.

Хранящиеся изображения считаются исходными баннерами и преобразуются новым renderer при следующем preview или join-событии. Изменение схемы БД не требуется, если не будет принято решение хранить дополнительные визуальные настройки.

## 22. Рекомендуемый административный UX

Чтобы настройка оставалась простой, группа команд должна разделять первичную настройку и точечные изменения:

| Команда | Назначение |
|---|---|
| `/welcome setup` | Первичная настройка либо полная перенастройка каналов, картинки, кнопки и текста |
| `/welcome edit` | Быстрое редактирование текста и названия кнопки через предзаполненную форму |
| `/welcome banner` | Замена только баннера |
| `/welcome preview` | Просмотр точного результата с аватаром администратора |
| `/welcome status` | Состояние, каналы и найденные проблемы |
| `/welcome enable` | Включение без потери настроек |
| `/welcome disable` | Отключение без потери настроек |

Рекомендация: не объединять все поля в одну большую форму. Discord modal не поддерживает загрузку attachment, поэтому текст и баннер всё равно удобнее редактировать отдельными командами.

### Новая зависимость

Предварительно подходит Pillow: библиотека работает внутри Railway-процесса и не требует отдельной подписки. Перед добавлением нужно проверить совместимость выбранной версии с используемой версией Python и сборкой Railway.

### Шрифт

Нельзя полагаться на наличие системного шрифта в Railway container. В репозиторий следует добавить локальный шрифт с подходящей лицензией и достаточной поддержкой кириллицы/латиницы. Emoji и редкие символы могут потребовать fallback-шрифт или безопасную замену при рендеринге.

## 24. Нефункциональные требования

- Генерация баннера не должна блокировать Discord event loop; CPU-операция должна выполняться вне основного async-потока.
- Avatar загружается только из URL, предоставленного Discord SDK для текущего участника.
- Для загрузки avatar должны быть определены timeout и ограничение размера ответа.
- Сбой avatar/renderer не должен останавливать бота или блокировать welcome-текст.
- В логах не сохраняются бинарные данные баннера/avatar и полный welcome-текст.
- Временные файлы не должны быть обязательны: обработка выполняется через `BytesIO` или безопасный временный файл с гарантированным удалением.
- Динамические изображения участников не сохраняются в БД и не образуют неограниченный кэш.
- Итоговый PNG должен укладываться в ограничения Discord attachment и существующий memory budget Railway; конкретный технический лимит фиксируется после прототипа.

## 25. Ошибки и альтернативные сценарии

| Ситуация | Ожидаемое поведение |
|---|---|
| Welcome не настроен, вызван `/welcome edit` | Понятное предложение сначала выполнить `/welcome setup` |
| Новая картинка повреждена | Отказ без изменения действующего баннера |
| Картинка имеет вертикальные пропорции | Центрированное масштабирование и crop в широкий баннер |
| Avatar отсутствует | Используется Discord default avatar |
| Avatar временно недоступен | Используется локальная заглушка или баннер без avatar; текст отправляется |
| Ник слишком длинный | Уменьшение шрифта, затем многоточие |
| Название сервера слишком длинное | Независимое уменьшение меньшего шрифта, затем многоточие |
| Ник содержит неподдерживаемые символы | Fallback-отрисовка без падения join handler |
| `{server_name}` повторяется несколько раз | Заменяются все вхождения |
| Шаблон не содержит `{server_name}` | Сообщение отправляется без дополнительного текста |
| Сервер переименован | Следующее сообщение использует новое имя автоматически |
| Renderer завершился ошибкой | Отправляется безопасный fallback и пишется структурированный warning |

## 26. Критерии приёмки этапа 2

1. Загруженная картинка отображается широким невысоким баннером в embed и не искажается.
2. Вертикальные, квадратные и широкие исходники приводятся к единому соотношению сторон предсказуемым центрированным crop.
3. На баннере видна круглая актуальная аватарка нового участника.
4. Справа от аватарки крупным шрифтом отображается `display_name` и не выходит за границы картинки.
5. Под ником меньшим шрифтом отображается актуальное название сервера; обе строки образуют центрированный по вертикали текстовый блок.
6. Вход bot account по-прежнему не создаёт welcome-сообщение.
7. `{server_name}` заменяется актуальным названием сервера в join-сообщении и preview.
8. Название сервера на баннере и значение `{server_name}` берутся из одного актуального `guild.name`.
9. `{user}` и правила безопасных упоминаний продолжают работать без регрессии.
10. `/welcome edit` показывает сохранённый текст, сохраняет изменения и не требует картинки или повторного выбора каналов.
11. `/welcome banner` меняет только баннер и не сбрасывает текст, каналы, кнопку и enabled-state.
12. Preview визуально использует тот же renderer, что и реальное welcome-сообщение.
13. Ошибка загрузки avatar не мешает отправке текста и баннера fallback.
14. Ошибка редактирования или невалидная картинка не повреждает действующую конфигурацию.
15. Существующая production-конфигурация работает сразу после обновления.
16. Все существующие welcome- и translation-тесты продолжают проходить.

# Этап 3: доработка баннера по результатам визуальной приёмки

## 31. Основание и цель этапа

Пользователь проверил текущий welcome-preview в Discord и предоставил визуальный референс. Текущий вариант функционально работает, но требует доработки композиции и правил обработки изображения.

Цель этапа — приблизить welcome-баннер к референсу по занимаемой ширине, оформлению фона и читаемости персонализированного текстового блока, сохранив небольшую высоту изображения в сообщении Discord.

## 32. Подтверждённые требования

### FR3-001 — Размер и начертание текста

- `display_name` должен выводиться более крупным и жирным шрифтом, чем в текущей версии.
- `guild.name` должен оставаться визуально вторичным, но стать крупнее и лучше читаться на фоне изображения.
- Между `display_name` и `guild.name` должен быть увеличен вертикальный отступ, чтобы строки не воспринимались как один плотный блок.
- Размеры шрифтов и отступ должны масштабироваться для длинных значений без выхода текста за безопасную область баннера.

### FR3-002 — Затемнение всего фона

- Полупрозрачное затемнение должно накладываться на всю площадь баннера, а не только на область вокруг аватара и текста.
- Затемнение должно сохранять различимость исходного изображения и обеспечивать читаемость белого текста на светлых и контрастных фонах.
- Локальная подложка под текст может использоваться только при необходимости и не должна выглядеть отдельным резко ограниченным прямоугольником.

### FR3-003 — Скругление баннера

- Итоговое изображение должно иметь визуально скруглённые углы по всему внешнему контуру.
- Области за скруглёнными углами должны быть прозрачными, чтобы в Discord не появлялись непрозрачные прямоугольные углы.
- Радиус должен быть единым для preview и сообщения о реальном входе участника.

### FR3-004 — Лимит загружаемого изображения

- Максимальный допустимый размер исходного banner-файла увеличивается с `2 МБ` до `5 МБ` включительно.
- Файл размером более `5 МБ` должен отклоняться до сохранения конфигурации с понятным сообщением о лимите.
- Изменение лимита не отменяет существующую проверку формата и размеров изображения.
- Документация администратора и troubleshooting должны указывать новый лимит `5 МБ`.

### FR3-005 — Пропорции и занимаемая область

- Баннер должен занимать максимально полезную ширину изображения внутри Discord embed, визуально ориентируясь на предоставленный референс.
- Высота баннера должна оставаться компактной: увеличение занимаемой ширины не должно превращать welcome-сообщение в высокую карточку.
- Композиция должна предусматривать аватар слева и текстовый блок справа с достаточной шириной для имени пользователя и названия сервера.
- Изображение не должно растягиваться с искажением пропорций; для приведения к итоговому холсту используется crop.
- Точный размер холста и aspect ratio выбираются после сравнительного preview в Discord, а не только по локальному PNG.

## 33. Визуальный ориентир

Референс задаёт следующие свойства, но не требует его буквального копирования:

- баннер заметно занимает ширину сообщения;
- внешний контур имеет хорошо заметное скругление;
- фон затемнён равномерно по всей площади;
- имя пользователя является главным визуальным акцентом;
- название сервера отделено от имени и остаётся читаемым;
- аватар и текст образуют одну сбалансированную горизонтальную композицию;
- итоговый баннер остаётся компактным по высоте.

Цветная внешняя рамка, слово `WELCOME` внутри изображения и дополнительные данные участника из референса в текущий этап не входят.

## 34. Критерии приёмки этапа 3

1. В Discord preview имя пользователя визуально крупнее и жирнее текущего варианта.
2. Между именем пользователя и названием сервера виден отдельный вертикальный отступ.
3. Название сервера читается на светлом, тёмном и контрастном тестовом фоне.
4. Затемнение равномерно покрывает всю площадь фонового изображения, без видимой границы локальной подложки.
5. У баннера видны скруглённые углы без непрозрачных прямоугольных областей за ними.
6. Файл размером ровно `5 МБ` принимается при соблюдении остальных ограничений.
7. Файл размером более `5 МБ` отклоняется, а существующая welcome-конфигурация не изменяется.
8. Горизонтальный баннер занимает доступную ширину Discord embed и остаётся компактным по высоте.
9. Длинные `display_name` и `guild.name` не выходят за границы, не пересекаются с аватаром и не обрезаются без предусмотренного fallback.
10. Preview и реальный join формируют визуально одинаковый баннер через единый renderer.
11. Результат проверен в desktop и mobile Discord.
12. Все существующие welcome- и translation-тесты продолжают проходить.

# Этап 4: единая welcome-карточка и настраиваемый цвет оформления

## 38. Основание и цель этапа

По результатам следующей визуальной проверки требуется объединить элементы welcome-сообщения в более цельную композицию и упростить оформление баннера.

Цель этапа — показывать текст и персонализированную картинку как одну Discord embed-карточку, визуально связать с ней кнопки, усилить начертание текста на баннере, убрать обводку аватара и текста, а также дать администратору возможность выбрать единый цвет оформления.

## 39. Ограничение Discord и выбранная интерпретация

Discord не позволяет буквально помещать кнопки внутрь embed-карточки. Кнопки являются message components и отображаются отдельным рядом под содержимым сообщения.

В рамках этапа 4 применяется ближайшее доступное поведение:

- обычный welcome-текст переносится из внешнего `content` в `description` того же embed, в котором находится баннер;
- баннер отображается внутри этого embed;
- кнопки прикрепляются к тому же сообщению и располагаются непосредственно под embed;
- у сообщения не должно оставаться отдельного текстового блока над карточкой;
- упоминание нового участника внутри embed должно сохранять текущее безопасное поведение без уведомлений `@everyone`, `@here` и ролей.

Такой вариант создаёт одну визуальную welcome-карточку в пределах возможностей Discord, но не гарантирует буквальное отображение кнопок внутри её рамки.

## 40. Подтверждённые требования этапа 4

### FR4-001 — Единый embed-контейнер

- Welcome-текст и персонализированный баннер должны находиться в одном Discord embed.
- Текст должен располагаться в `description` embed, а баннер — в области изображения этого же embed.
- Отдельный `content` над embed не должен использоваться для welcome-текста.
- Баннер должен занимать доступную ширину embed и восприниматься центрированным относительно текста карточки.
- Preview и реальный join должны использовать одинаковую структуру сообщения.

### FR4-002 — Кнопки welcome-сообщения

- Основная и будущие дополнительные кнопки должны оставаться компонентами того же Discord-сообщения.
- Кнопки должны отображаться непосредственно под embed без постороннего текста или дополнительных сообщений между карточкой и кнопками.
- Невозможность поместить кнопки внутрь embed считается ограничением платформы, а не дефектом реализации.

### FR4-003 — Более жирный текст на баннере

- `display_name` должен использовать более тяжёлое доступное начертание, чем в текущей версии.
- `guild.name` также должен выводиться жирным шрифтом, оставаясь визуально вторичным за счёт меньшего размера и менее яркого цвета.
- При отсутствии системного шрифта с требуемой насыщенностью renderer должен использовать предсказуемый локальный fallback.
- Усиление начертания не должно нарушать обработку длинных имён и безопасную область текста.

### FR4-004 — Удаление обводки аватара и текста

- Белая обводка вокруг круглого аватара должна быть удалена.
- Контур `stroke` вокруг `display_name` и `guild.name` должен быть удалён.
- Читаемость текста после удаления обводки должна обеспечиваться общим затемнением фоновой картинки, цветом текста и выбранным начертанием.
- Круглая маска аватара и прозрачное скругление внешних углов баннера должны сохраниться.

### FR4-005 — Настраиваемый цвет оформления

- Администратор должен иметь возможность задать цвет оформления welcome-карточки в формате HEX `#RRGGBB`.
- Один выбранный цвет должен применяться одновременно к внешней рамке сгенерированного баннера и цветовому акценту Discord embed.
- Цвет должен храниться отдельно для каждого `guild_id` и применяться к preview и реальному join.
- Невалидное значение не должно сохраняться или частично изменять действующую welcome-конфигурацию.
- Для существующих конфигураций должен использоваться фиолетовый цвет по умолчанию `#5865F2`.
- Discord управляет внешним видом embed самостоятельно: настраивается его цветовой акцент, но не полный CSS-контур контейнера со всех сторон.

### FR4-006 — Простое редактирование цвета

- Изменение цвета не должно требовать повторного прохождения полной команды `/welcome setup`.
- Настройка должна выполняться отдельной сфокусированной операцией в существующей группе `/welcome`.
- После сохранения нового цвета бот должен показать preview либо предложить сразу запустить `/welcome preview`.
- Изменение цвета не должно перезаписывать каналы, текст, баннер, кнопку или состояние `enabled`.

## 41. Данные и влияние на компоненты

Для каждой welcome-конфигурации требуется хранить нормализованный цвет оформления, например `accent_color` в формате `RRGGBB` или как целое RGB-значение. Конкретный тип выбирается при реализации с учётом совместимости SQLite и PostgreSQL.

Существующие записи должны продолжить работать после обновления схемы и получить безопасное значение по умолчанию без повторной настройки администратора.

### Затрагиваемые компоненты

# Этап 5: исправление рамки баннера и кликабельные ссылки на каналы

## 46. Основание и цель этапа

Проверка welcome-карточки в Discord выявила два замечания:

1. Фоновое изображение визуально выходит за цветную рамку баннера.
2. Указанные в welcome-тексте каналы не открываются по нажатию.

Цель этапа — ограничить изображение внутренним контуром рамки и обеспечить надёжные кликабельные переходы в каналы текущего Discord-сервера непосредственно из текста embed.

## 47. Анализ текущего поведения

### Рамка баннера

Сейчас скругляющая маска применяется ко всему холсту, после чего цветная рамка рисуется поверх изображения с отступом от края. Из-за этого фон присутствует по обе стороны линии рамки и визуально воспринимается как выходящий за её внешний контур.

Требуется разделить внешний контур PNG, область рамки и внутреннюю область изображения. Фон, аватар и текст должны быть обрезаны внутренней скруглённой маской, рамка должна занимать отдельную полосу, а пиксели за её внешним контуром должны оставаться прозрачными.

### Ссылки на каналы

Обычный текст `#channel-name` не содержит идентификатора канала и не является надёжной ссылкой в Discord embed. Токен `<#channel_id>` сохраняется текущей обработкой, но его отображение как интерактивного упоминания внутри embed зависит от поведения клиента Discord и по результату проверки не обеспечивает требуемый переход.

Надёжный поддерживаемый вариант — Markdown-ссылка на URL канала:

```text
[#rules](https://discord.com/channels/GUILD_ID/CHANNEL_ID)
```

Бот должен формировать такую ссылку самостоятельно из проверенного `guild_id` и `channel_id`, а администратор не должен вручную собирать Discord URL.

## 48. Требования этапа 5

### FR5-001 — Внутренняя граница изображения

- Фоновая картинка, аватар и текст баннера не должны отображаться снаружи внутреннего края цветной рамки.
- Область между внутренней и внешней границами должна быть полностью занята выбранным цветом рамки.
- Пиксели за внешним скруглённым контуром рамки должны быть прозрачными.
- Толщина рамки и радиусы должны быть одинаковыми для preview и реального join.
- Исправление не должно менять размер холста `1200×420` или искажать пропорции исходного изображения.

### FR5-002 — Поддерживаемая запись ссылки в шаблоне

- В welcome-тексте должна поддерживаться запись канала в виде `<#channel_id>`.
- При формировании сообщения бот должен преобразовывать валидную запись канала в Markdown-ссылку с читаемым названием: `[#channel-name](https://discord.com/channels/guild_id/channel_id)`.
- Администратор также может вставить полный URL канала, полученный через Discord `Copy Channel Link`; валидный URL текущего сервера должен нормализоваться в тот же формат.
- Обычный текст вида `#channel-name` без ID не должен автоматически преобразовываться, поскольку названия каналов могут повторяться.

### FR5-003 — Проверка назначения ссылки

- Ссылка должна вести только в канал текущего `guild_id`.
- Перед preview или отправкой бот должен проверить, что канал существует в доступном кэше сервера.
- Ссылка на другой сервер, удалённый канал или некорректный ID не должна превращаться в кликабельную ссылку.
- При невалидном назначении сообщение не должно падать; проблемная запись остаётся безопасным текстом, а `/welcome status` должен сообщить о некорректной ссылке.
- Возможность открыть канал для конкретного участника определяется правами Discord; бот не должен обходить channel permissions.

### FR5-004 — Безопасность текста

- Преобразование каналов не должно ослаблять текущую защиту от `@everyone`, `@here`, упоминаний ролей и посторонних пользователей.
- Разрешённое упоминание нового участника через `{user}` должно продолжить работать.
- Название канала, подставляемое в Markdown label, должно экранироваться так, чтобы специальные символы не ломали ссылку или остальной текст.
- Произвольные внешние URL не должны автоматически получать доверенный channel-label.

### FR5-005 — Административный UX

- В описании поля welcome-текста и документации должен быть приведён понятный пример `<#channel_id>` и способ получить его через Discord.
- Preview должен показывать итоговую кликабельную ссылку до включения или сохранения изменённого текста, если текущий поток команды позволяет preview после сохранения.
- Для простой ссылки на канал не должна добавляться новая отдельная slash-команда.

## 49. Критерии приёмки этапа 5

2. Вся полоса рамки имеет выбранный цвет без участков исходного изображения поверх неё.
3. Угловые пиксели за внешним скруглением прозрачны.

11. Пользователь без права `View Channel` не получает доступ к закрытому каналу через ссылку.

13. `/welcome status` сообщает о невалидных ссылках на каналы в сохранённом шаблоне.
14. Поведение проверено в desktop и mobile Discord.

# Этап 6: напоминания и ежедневная очистка выбранных каналов

## 53. Основание и цель этапа

Welcome-функционал этапа 5 вручную проверен пользователем и работает. Следующая доработка должна добавить две независимые guild-scoped функции:

1. создание и управление одноразовыми и повторяющимися напоминаниями;
2. ежедневную тихую очистку сообщений в выбранных каналах с сохранением pinned-сообщений.

На этом этапе выполняются анализ и планирование. Production-код не изменяется.

## 54. Подтверждённый объём

### Входит в этап

- группа slash-команд `/reminder` с подкомандами `list`, `add`, `edit`, `remove`;
- одноразовые напоминания на конкретную дату;
- повторение каждый день, каждую неделю и каждый месяц;
- множитель периодичности `every`, например каждые 2 дня или каждые 4 недели;
- отправка заранее на `offset_minutes` либо точно во время события;
- необязательная начальная дата повторения `start_date`;
- необязательное упоминание `@everyone` или `@here`;
- выбор существующего напоминания для `edit` и `remove` по ID через Discord autocomplete;
- простой вывод сообщения без пользовательского Markdown-форматирования;
- ежедневная очистка сообщений в одном или нескольких выбранных администратором каналах;
- ежедневная очистка уже отправленных сообщений в выбранных каналах без удаления самих reminder-настроек;
- отдельное хранение конфигурации для каждого Discord-сервера;
- работа с SQLite локально и PostgreSQL на Railway.

### Не входит без отдельного решения

- личные напоминания в DM;
- сложные cron-выражения;
- интервалы короче одного дня;
- годовые повторения;
- вложения, изображения, кнопки и пользовательское оформление напоминаний;
- изменение существующей welcome- и translation-логики;
- восстановление удалённых сообщений;
- очистка каналов по содержимому, автору или регулярному выражению.

## 55. Термины и роли

### Reminder

Guild-scoped запись с текстом, каналом назначения, временем события, правилом повторения и временем фактической отправки с учётом `offset_minutes`.

### Event time

Момент события в UTC. Напоминание отправляется в `event time - offset_minutes`.

### Cleanup rule

Guild-scoped правило ежедневной очистки уже отправленных сообщений в одном выбранном текстовом канале. Оно не удаляет записи Reminder из БД.

### Администратор сервера

Создаёт, просматривает, изменяет и удаляет напоминания и правила очистки. Предлагаемое разрешение — `Manage Server`, как у существующих административных команд проекта.

### Бот

Восстанавливает расписание после перезапуска, отправляет наступившие напоминания не более одного раза на конкретное occurrence, выполняет очистку и ведёт структурированные операционные логи.

## 56. UX slash-команд Reminder

### `/reminder list`

- показывает только напоминания текущего сервера;
- каждая строка содержит как минимум ID, `title` и краткое человекочитаемое расписание;
- список сортируется по ближайшему времени фактической отправки;
- длинный список должен поддерживать разбиение на страницы либо иной интерфейс в пределах ограничений Discord;
- ответ администратора предлагается делать ephemeral;
- визуальный ориентир из приложенного скриншота: компактный список настроек вида `ID · title · daily 17:50`.

### `/reminder add`

Создаёт напоминание после полной проверки полей и показывает сохранённое расписание и ближайший запуск. Создание не должно происходить частично при ошибке одного поля.

### `/reminder edit id:<reminder_id>`

- поле `id` обязательно;
- Discord autocomplete показывает напоминания только текущего сервера в формате, позволяющем различить ID, название и расписание;
- после выбора запись редактируется без необходимости вручную искать или копировать ID;
- поля, которые администратор не меняет, сохраняют текущие значения;
- итоговый ответ показывает обновлённое расписание и ближайший запуск.

Discord ограничивает число параметров slash-команды, поэтому окончательный способ редактирования всех полей — параметры команды, modal или последовательный интерактивный редактор — должен быть выбран после закрытия вопросов раздела 65.

### `/reminder remove id:<reminder_id>`

- поле `id` обязательно и использует тот же guild-scoped autocomplete;
- удаляется только выбранное напоминание текущего сервера;
- неизвестный или принадлежащий другому серверу ID возвращает понятную ошибку;
- после удаления бот подтверждает ID и название удалённой записи;
- перед окончательным удалением бот запрашивает явное подтверждение.

## 57. Поля Reminder

| Поле | Статус | Правило |
|---|---|---|
| `id` | системное | Уникальный стабильный идентификатор записи; используется в `edit`, `remove` и `list` |
| `repeats` | подтверждено | Discord choice: `once`, `daily`, `weekly`, `monthly`; интервалы every other/every 4 задаются через `every`, а не отдельными значениями |
| `channel` | подтверждено | Текстовый канал текущего сервера, куда бот отправляет напоминание |
| `time` | подтверждено | Время события в формате `HH:MM` UTC |
| `message` | подтверждено | Обязательный plain-text body длиной `1..1800` символов |
| `date` | подтверждено для одноразового сценария | Дата `YYYY-MM-DD` UTC; применима к `once` |
| `weekday` | подтверждено для weekly | Discord choice `Monday`…`Sunday` для `weekly` |
| `day_of_month` | подтверждено для monthly | Целое число `1..31`; если такого дня в месяце нет, occurrence месяца пропускается |
| `every` | подтверждено | Целое число `1..365`; default `1`; задаёт каждые N дней, недель или месяцев |
| `offset_minutes` | подтверждено | Целое число `0..10080`; default `0`; запуск = event time минус offset |
| `start_date` | подтверждено как optional | Anchor `YYYY-MM-DD` только для повторений; default — ближайшая допустимая дата не раньше текущей UTC-даты |
| `mention_everyone_or_here` | подтверждено как выбор | Discord choice `none`, `everyone`, `here`; default `none` |
| `title` | подтверждено | Plain-text заголовок длиной `1..100` символов, первая строка сообщения, без разрешённых mentions |

Название `mention_everyone_or_here` сохранено из запроса. Поле реализуется не как Boolean, а как выбор из `none`, `everyone`, `here`.

На одном сервере допускается до 100 Reminder-записей. Для `every` установлен максимум 365. Эти пределы оставляют достаточный административный запас и ограничивают стоимость фонового опроса, списка и восстановления после простоя.

## 58. Функциональные требования Reminder

### FR6-R01 — Изоляция серверов

Бот должен хранить, показывать, изменять, запускать и удалять напоминания только в пределах соответствующего `guild_id`.

### FR6-R02 — Одноразовое расписание

Для `once` бот должен принять UTC-дату и UTC-время события, вычислить время отправки с учётом offset и после успешной отправки больше не запускать это occurrence.

Создание записи, чьё рассчитанное время отправки уже прошло, должно быть отклонено либо обработано по отдельно утверждённому правилу.

### FR6-R03 — Ежедневное расписание

Для `daily` occurrence повторяется каждые `every` дней от `start_date`. Если `start_date` не указана, anchor — ближайшая допустимая дата не раньше текущей UTC-даты.

### FR6-R04 — Еженедельное расписание

Для `weekly` occurrence повторяется в выбранный `weekday` каждые `every` недель относительно anchor.

### FR6-R05 — Ежемесячное расписание

Для `monthly` occurrence повторяется в `day_of_month` каждые `every` месяцев относительно anchor. Если целевого дня 29–31 в конкретном месяце нет, occurrence этого месяца пропускается; отправка не переносится на последний день месяца.

### FR6-R06 — Упреждение

`offset_minutes=0` означает отправку в event time. Значение от 1 до 10080 означает отправку на соответствующее число минут раньше. В `list` и ответах `add/edit` должны быть видны и event time, и offset, чтобы избежать неоднозначности.

### FR6-R07 — Доставка сообщения

Бот должен отправлять напоминание в выбранный канал текущего сервера. Текст не должен проходить через AI-перевод или существующий translation relay.

До сохранения бот проверяет, что канал существует и у него есть `View Channel` и `Send Messages`. Если используется embed, дополнительно требуется `Embed Links`.

### FR6-R08 — Безопасность упоминаний

По умолчанию все упоминания должны быть отключены через явный `AllowedMentions`. Только выбор `everyone` либо `here` может разрешить соответствующее массовое упоминание. Бот сам добавляет выбранное упоминание отдельной последней строкой после `message body`.

Упоминания внутри `title` запрещены и всегда нейтрализуются. Произвольные пользовательские, ролевые и массовые упоминания, введённые непосредственно в title или body, не должны срабатывать. Для настройки и фактического ping бот проверяет права администратора и собственное право `Mention Everyone`.

### FR6-R09 — Autocomplete

Autocomplete для `edit` и `remove` не должен раскрывать записи других серверов. При вводе текста результаты фильтруются по ID и названию и учитывают лимит вариантов Discord.

### FR6-R10 — Изменение расписания

После `edit` будущий запуск должен быть пересчитан атомарно. Уже отправленные occurrences не повторяются. Изменение записи во время её выполнения не должно приводить к двойной отправке. Временное enable/disable не поддерживается: запись либо активна, либо удалена через `remove`.

### FR6-R11 — Перезапуск и пропущенные запуски

Расписание должно храниться в БД, а не только в памяти. После запуска бот восстанавливает ближайшие occurrences.

Если во время простоя было пропущено одноразовое напоминание, оно ставится в очередь немедленной отправки. Для повторяющейся записи бот отправляет только самое позднее пропущенное occurrence; все более ранние occurrences этой же записи считаются пропущенными и не воспроизводятся.

Чтобы после длительного простоя сервер не получил десятки сообщений одновременно, catch-up отправки выполняются контролируемой очередью: не более 5 сообщений на один guild в минуту. Очередь не отменяет актуальные будущие запуски и опирается на устойчивые execution-записи.

### FR6-R12 — Защита от дублей

Для каждого occurrence должен существовать устойчивый ключ выполнения. Повторный tick планировщика, reconnect или ошибка после отправки не должны создавать неконтролируемые дубли. Текущая Railway-конфигурация с одним процессом упрощает исполнение, но не отменяет необходимость идемпотентности.

### FR6-R13 — Ошибки доставки

Удалённый канал, потеря прав или ошибка Discord не должны останавливать фонового исполнителя. Бот записывает структурированную ошибку и применяет утверждённую retry-политику.

## 59. Формат отправляемого Reminder

Напоминание отправляется как обычное Discord message content, без embed. Это исключает отображение `**` в push-уведомлении и не требует права `Embed Links`.

Формат payload:

```text
title
message body

@everyone или @here — только если выбран соответствующий mention mode
```

- `title` — первая plain-text строка, без Markdown и без активных mentions;
- `message body` начинается со следующей строки;
- выбранный ботом массовый mention добавляется только внизу body отдельной последней строкой;
- `title` и `message` очищаются от управляющего Markdown-форматирования, а введённые вручную mentions не активируются;
- суммарный payload не должен превышать лимит Discord `2000` символов; лимиты `title=100` и `message=1800` оставляют запас для переносов строки и mention.

## 60. Ежедневная очистка каналов

### Административный интерфейс

Для настройки используется отдельная группа:

- `/cleanup list` — показать правила текущего сервера;
- `/cleanup add` — выбрать очищаемый канал;
- `/cleanup edit` — выбрать правило через autocomplete и изменить его;
- `/cleanup remove` — удалить правило.

`edit` и `remove` используют guild-scoped autocomplete. Удаление правила требует явного подтверждения. Одновременно допускается до 25 правил на сервере и не более одного правила на один канал.

### FR6-C01 — Область очистки

Каждое правило относится ровно к одному выбранному текстовому каналу текущего сервера. Возможность создать несколько правил позволяет очищать несколько каналов без глобального удаления. Правило удаляет опубликованные сообщения, а не Reminder-записи из БД.

### FR6-C02 — Периодичность

Очистка выполняется один раз в день в заданное для правила время `HH:MM UTC`. Default — `00:00 UTC`; каждый выбранный канал может иметь собственное время.

### FR6-C03 — Состав удаления

В выбранном канале удаляются все доступные сообщения независимо от автора и времени публикации, кроме pinned-сообщений. Настройки Reminder и Cleanup в БД не затрагиваются.

### FR6-C04 — Без уведомления

После успешной или пустой очистки бот не публикует в канале никаких сообщений, включая количество удалённых сообщений. Результат отражается только в структурированных операционных логах.

### FR6-C05 — Права и ограничения Discord

Перед включением правила бот проверяет `View Channel`, `Read Message History`, `Manage Messages` и `Send Messages`. Ошибка удаления отдельного сообщения не должна останавливать обработку остальных доступных сообщений.

План должен учитывать ограничение Discord bulk delete для старых сообщений: сообщения, которые нельзя удалить пакетно, обрабатываются поддерживаемым Discord способом без обхода API-ограничений.

### FR6-C06 — Безопасность операции

Очистка должна быть ограничена явно сохранённым `guild_id + channel_id`. Удаление в другом канале, по имени канала или по неразрешённому динамическому target запрещено.

### FR6-C07 — Перезапуск и дубли

Правила хранятся в БД и восстанавливаются после рестарта. Для каждой календарной даты UTC должна фиксироваться попытка выполнения, чтобы reconnect или повторный tick не запускали параллельные очистки одного правила.

### FR6-C08 — Отчёт об ошибке

Если очистка полностью или частично не выполнена, ошибка фиксируется в структурированном логе. Сообщение в очищаемый канал не публикуется.

- `id`;

- фактическое время попытки;

- `guild_id`;
- `channel_id`;

- `last_run_date_utc`;
- `created_by_user_id`;
- `created_at`;
- `updated_at`.

## 62. Нефункциональные требования

- Фоновая ошибка reminder или cleanup не должна останавливать welcome и translation-функции.
- Исполнитель не должен зависеть от активного Discord interaction после сохранения настройки.
- Текст напоминаний не должен попадать в обычные операционные логи.
- В логах допустимы IDs сервера, канала, правила, occurrence, статус и тип ошибки.
- Все расчёты и сохранённые моменты времени должны иметь явно определённую UTC-семантику.
- Работа с SQLite и PostgreSQL должна быть эквивалентной.
- Новые таблицы создаются без потери существующих данных.
- Отправка и очистка должны учитывать rate limits Discord и не использовать блокирующие операции в event loop.
- Завершение бота должно корректно останавливать фоновые задачи до закрытия соединения с БД.

## 63. Критерии приёмки Reminder

1. Администратор может создать валидное одноразовое напоминание и увидеть его в `/reminder list`.
2. Daily-, weekly- и monthly-правила вычисляют ожидаемое следующее occurrence при `every=1`, `2` и `4`.
3. `offset_minutes=0` отправляет в event time, а `10`, `15` и `10080` — на соответствующее время раньше.
4. Значения offset меньше 0 или больше 10080 отклоняются без создания или частичного изменения записи.
5. Невалидные даты, время, weekday, day of month и `every<1` отклоняются понятной ошибкой.
6. `edit` и `remove` предлагают через autocomplete только напоминания текущего сервера.
7. Изменение одного поля не сбрасывает остальные поля записи.
8. Удалённое напоминание больше не запускается.
9. После рестарта будущие напоминания восстанавливаются из БД.
10. Один occurrence не отправляется дважды при повторном tick или reconnect.
11. Удалённый канал или потеря прав не останавливают остальные напоминания.
12. Без явного выбора массового упоминания сообщение не пингует `@everyone`, `@here`, роли или пользователей.
13. При разрешённом режиме выполняется только выбранный ping `@everyone` либо `@here`.
14. Текст напоминания отправляется без AI-перевода и пользовательского Markdown-оформления.
15. Записи одного сервера нельзя просмотреть, изменить, удалить или запустить с другого сервера.

## 64. Критерии приёмки Cleanup

1. Администратор может создать правило только для текстового канала текущего сервера.
2. В назначенное UTC-время правило запускается не более одного раза за календарную дату.
3. Удаляются только сообщения, попадающие под утверждённый критерий правила.
4. Pinned-сообщения сохраняются либо удаляются строго по утверждённой политике.
5. После успешной или пустой очистки бот не публикует уведомление в канале.
6. Бот корректно обрабатывает сообщения старше лимита bulk delete.
7. Потеря `Manage Messages`, удаление канала или частичная ошибка не останавливают другие правила.
8. После рестарта правила восстанавливаются из БД без двойного запуска.
9. Правило одного сервера невозможно применить к каналу другого сервера.
10. Все существующие welcome- и translation-тесты продолжают проходить.

# Этап 6.1: поддержка emoji и исправление выбора Reminder для редактирования

## 69. Основание и цель правок

По результатам проверки Reminder выявлены два дефекта:

1. `title` и `message` не обеспечивают сохранение и корректную отправку стандартных Unicode emoji и кастомных Discord emoji.
2. В `/reminder edit` Discord показывает guild-scoped список напоминаний, однако после выбора элемента параметр `reminder_id` отклоняется как нечисловой. В результате администратор не может перейти к редактированию выбранной записи.

Цель этапа 6.1 — разрешить emoji в обоих текстовых полях Reminder и восстановить простой выбор существующего напоминания кликом по варианту autocomplete без ручного копирования числового ID.

К реализации этапа 6.1 приступать только после отдельного подтверждения пользователя.

## 70. Анализ текущего поведения

### Emoji

- `title` и `message` сохраняются в БД как строки и перед отправкой проходят через `safe_text`.
- `safe_text` одновременно нейтрализует Discord mentions и удаляет Markdown. Общее удаление Markdown не закрепляет сохранность Discord-синтаксиса кастомных emoji и является наиболее вероятной точкой потери emoji.
- Защита от пользовательских, ролевых и массовых mentions должна сохраниться. Разрешение emoji не должно разрешать произвольные ping.
- Изменение схемы БД не требуется: текущие строковые поля могут хранить Unicode и текстовый Discord-синтаксис кастомных emoji.

### Выбор Reminder для edit

- `/reminder edit` принимает `reminder_id` как Discord integer option.
- Autocomplete отображает человекочитаемую строку `ID · title · schedule`, но возвращает числовое значение.
- В наблюдаемом клиентском сценарии после выбора Discord требует ввести число и не позволяет выполнить команду.
- Рекомендуемое исправление — принимать выбранное значение как строковый option, возвращать ID из autocomplete строкой и строго преобразовывать его в целое число внутри команды перед guild-scoped поиском записи.
- Под «редактированием по клику» в рамках этой правки понимается выбор напоминания кликом из autocomplete `/reminder edit`, после чего остальные изменяемые поля заполняются в той же slash-команде. Отдельное интерактивное меню с кнопками и modal-формами в объём этапа не входит.

## 71. Функциональные требования этапа 6.1

### FR6.1-01 — Стандартные emoji

Система должна принимать, сохранять, показывать при последующей отправке и разрешать редактирование стандартных Unicode emoji в `title` и `message` Reminder.

Emoji должны сохраняться без замены, удаления или добавления разделителей внутрь Unicode-последовательности, включая составные emoji и варианты с модификатором тона кожи.

### FR6.1-02 — Кастомные Discord emoji

Система должна сохранять и отправлять статические кастомные Discord emoji вида `<:name:id>` и анимированные emoji вида `<a:name:id>` в `title` и `message` Reminder.

Если Discord не может отобразить emoji из-за удаления emoji, отсутствия доступа к нему или ограничений сервера, Reminder не должен аварийно завершать фоновый исполнитель. Ответственность за фактическую доступность кастомного emoji остаётся у Discord; бот сохраняет исходную ссылку на emoji без преобразования.

### FR6.1-03 — Совместимость с mention safety

Поддержка emoji не должна менять правила mentions:

- пользовательские и ролевые mentions, введённые в `title` или `message`, не активируются;
- `@everyone` и `@here`, введённые вручную, не активируются;
- активный `@everyone` или `@here` добавляется только существующим механизмом `mention_everyone_or_here` в последней строке сообщения;
- синтаксис emoji не должен ошибочно распознаваться как mention и нейтрализовываться.

### FR6.1-04 — Выбор Reminder в `/reminder edit`

При вводе `/reminder edit` администратор должен получить autocomplete только с Reminder текущего сервера. Каждый вариант должен содержать ID, title и краткое расписание.

После клика по варианту Discord должен принять выбранное значение без требования повторно вводить числовой ID. Администратор должен иметь возможность заполнить одно или несколько изменяемых полей и успешно выполнить команду.

Перед обновлением система должна строго проверить, что выбранное значение является целочисленным ID существующего Reminder текущего сервера. Некорректное, устаревшее или относящееся к другому серверу значение не должно изменять данные.

### FR6.1-05 — Согласованность выбора для удаления

Поскольку `/reminder edit` и `/reminder remove` используют общий autocomplete, исправленный строковый контракт выбора ID должен применяться к обеим командам. Существующее подтверждение удаления сохраняется.

## 72. Критерии приёмки этапа 6.1

1. Reminder со стандартными emoji в `title` и `message` создаётся, хранится и отправляется с теми же emoji.
2. Составной Unicode emoji не разбивается и не искажается при отправке.
3. Статический кастомный emoji `<:name:id>` отображается в отправленном Reminder при наличии доступа Discord к emoji.
4. Анимированный кастомный emoji `<a:name:id>` отображается в отправленном Reminder при наличии доступа Discord к emoji.
5. Одно сообщение может одновременно содержать стандартные и кастомные emoji в `title` и `message`.
6. Добавление поддержки emoji не активирует пользовательские, ролевые, `@everyone` или `@here` mentions из введённого текста.
7. `/reminder edit` показывает только записи текущего сервера и позволяет выбрать нужную запись кликом по autocomplete.
8. После выбора записи администратор может изменить отдельно `title`, `message` или любой другой поддерживаемый параметр без ручного ввода ID.
9. Некорректный строковый ID возвращает понятную ephemeral-ошибку и не изменяет Reminder.
10. ID существующего Reminder другого сервера обрабатывается как отсутствующий и не раскрывает его содержимое.
11. `/reminder remove` продолжает выбирать запись через autocomplete и требовать подтверждение.
12. Существующие тесты расписаний, дедупликации, mentions, Cleanup и Welcome продолжают проходить.
